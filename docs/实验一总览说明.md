# 实验一到底在干什么

> 用途：理清这次实验的脉络，兼作答辩 / 面试复习提纲。
> 细节都在 `specs/` 下对应文档里，本文件只讲**整体逻辑与取舍理由**。

---

## 一、一句话

实验一不是"画图"，而是：

> **把图书管理系统的业务需求，逐层翻译成一份「可以直接照着写代码」的设计契约**，
> 全程由 AI 起草、人类拍板、Git 留痕。

画出来的 UML 只是这份契约的**可视化表达**，图本身不是目的。

---

## 二、这门课为什么这么改

| 传统软件工程 | AI 时代的软件工程（本实验） |
|---|---|
| 人分析需求 | 人给**目标与约束** |
| 人画 UML | Agent 起草规格与图，**人审查修订** |
| 人设计架构 | Agent 出架构方案，人拍板 |
| 人写代码 | 冻结 Specs → Agent 按任务实现 |
| 人测试 | 测试先行约束实现 |
| 交一份报告 | 交 Specs + UML + 代码 + 测试 + **AI 使用记录** |

**所以评分看的不是"代码跑不跑得起来"，而是文档的完整性与正确性。**

指导书原文：考核方式 = 实验报告，主要考核**文档的完整性、正确性**，
架构设计与详细设计**各占 50%**。

对应到两个实验：

- **实验一 = 架构设计**（占 50%）← 本次已完成
- **实验二 = 详细设计 + 代码**（占 50%）← 下一步

## 三、五步在干什么：一条推导链

指导书的 5 个步骤**不是五份独立作业**，而是一条链：
**每一步回答一个具体问题，前一步的输出是后一步的输入。**

| 步骤 | 回答的问题 | 产出 | 不做什么 |
|---|---|---|---|
| **1 用例** | 系统**给谁用、能干什么**？ | 5 类参与者、17 个用例、5 个核心用例的三流 | 不涉及类和数据库 |
| **2 领域** | 这些事牵扯**哪些业务概念**？ | 14 个实体、7 个值对象、2 个策略、2 个领域服务 | 不出现 Controller/Repository |
| **3 架构** | 代码**怎么分层、谁依赖谁**？ | 四层 + MVC、7 模块、权限/异常/事务策略、8 个设计模式 | 不写具体方法实现 |
| **4 设计** | 每个类**长什么样、怎么协作**？ | 分析类图 → 设计类图 + 3 张顺序图 + 领域层 Java 骨架 | 不实现完整业务 |
| **5 数据库** | **哪些类要存、怎么存**？ | 11 张表 + 索引 + 约束 + 实跑验证 | 不写业务代码 |

### 同一条线索在五步里的演变

以"借书要验证借阅证"为例，看它怎么一层层长出来：

```
步骤1 用例       UC-901「验证借阅证」被 UC-101「借书」include
   ↓
步骤2 领域       领域类 BorrowCard 出现，带 cardNo / status / isValid()
   ↓
步骤3 架构       划分出 card 模块；业务规则归属 → 不放 Controller
   ↓
步骤4 设计       BorrowCardRepository 接口（领域层）+ JpaBorrowCardRepository（基础设施层）
   ↓
步骤5 数据库     borrow_cards 表，card_no UNIQUE，status 带 CHECK 约束
```

**这条链就是实验一的骨架。** 答辩时如果被问"你的设计是怎么来的"，顺着这条链讲，
比背文档目录有说服力得多。

## 五、四个关键决策，以及为什么这么选

这部分是**答辩最容易被追问**的地方，每个都按"面临什么选择 / 选了什么 / 为什么不选另一个"记。

### 决策 1：读者类型差异，不做独立用例

- **面临**：指导书说 5 类读者的借阅数量和期限都不同。要不要给每类读者各立一套"借书"用例？
- **选了**：不立。只立一个 UC-101「办理借书」，差异交给被包含的 UC-902「检查借阅规则」内部的 `BorrowPolicy` 处理。
- **为什么**：用例描述的是**用户目标**，不是**规则分支**。5 类读者 × 借/还/预约 = 15 个几乎一样的用例，是典型的用例爆炸，维护成本远大于收益。
- **怎么支撑**：`borrow_policies` 表按 `reader_type` 存规则，`BorrowPolicy` 是 Strategy 模式的策略对象。新增一种读者类型 = 加一行数据 + 一个枚举值，**不改借书流程代码**（开闭原则）。

### 决策 2：继承映射用单表，不用每类一表

- **面临**：`Reader → StudentReader / TeacherReader`、`LibraryItem → Book / Magazine / Thesis`，两组继承怎么落库？
- **选了**：**单表 + 判别列**（`readers.reader_type`、`library_items.item_type`）。
- **为什么**：子类字段差异很小（2–3 个），而借书主流程要频繁查读者和副本——单表不用 JOIN，代价只是几个 NULL 列。作业量级下，11 张表比 16 张表好讲清楚。
- **代价怎么补**：用 `CHECK` 约束保证一致性，例如教师不能有学号（已实测生效）。

### 决策 3：领域层零框架依赖

- **面临**：实体上直接加 `@Entity` `@Table` 最省事，要不要这么干？
- **选了**：不。领域实体是纯 Java，另外有 `LoanPO` 等持久化对象；Repository 接口定义在领域层，实现放基础设施层。
- **为什么**：领域层一旦被 JPA 注解污染，就没法脱离框架单独测试，业务规则也被绑死在表结构上。这是**依赖倒置**——高层（领域）定义接口，低层（基础设施）去实现。
- **怎么证明**：领域层不需要 Maven，直接 `javac` 就能编译（已实测，36 个文件 0 错误）。这条硬证据比嘴上说"我分层了"有力得多。

### 决策 4：异常用错误码枚举，不是一异常一类

- **面临**：每种业务失败要不要各写一个异常类（`CardNotFoundException`、`QuotaExceededException`…）？
- **选了**：统一 `BusinessException(ErrorCode, detail)`，`ErrorCode` 枚举里带 HTTP 状态码和默认中文提示。
- **为什么**：20 种失败 = 20 个类，但表现层要做的其实是同一件事——**映射成 HTTP 语义**。用枚举把"错误类型 → HTTP 状态 → 提示语"集中管理，加一种错误只加一个枚举值。
- **边界**：确实需要不同 catch 行为时才升级成独立异常类，目前没有这种需求。

## 六、AI 在这次实验里到底干了什么

这是本课程区别于传统实验的地方，答辩大概率会问"你在哪用了 AI"。

| 环节 | AI（WorkBuddy） | 人类（Violet） |
|---|---|---|
| 起草 Specs | 全部 15 份文档、8 张 UML、36 个 Java 文件的初稿 | — |
| 需求澄清 | 整理出 7 组待确认假设 | **拍板确认** |
| 范围决策 | 指出 Word 指导书与 AI 手册在"顺序图归属"上的冲突 | **决定按指导书** |
| 数据库 | 设计 + 写 DDL + 实跑验证 | 提供访问凭据 |
| 提交 | 执行 git commit / push | **审查 diff 后决定** |

**关键点**：AI 起草 ≠ AI 决定。所有取值、范围、可见性都是人拍的板，而且**每一次都留了痕**
（`docs/实验过程日志.md` 标了 `[AI]` / `[人工]`，`specs/19-ai-usage-log.md` 逐条记录）。

**这次 AI 还揪出了自己的一个错**：数据库文档初稿写"7 处外键"，实跑后发现是 9 处，已更正并留修正记录。
这正好演示了本课程想教的事——**AI 会出错，所以要验证，要人工审查**。

## 七、答辩可能被问的问题

| 问题 | 怎么答 |
|---|---|
| 你的设计从哪来？ | 顺着第三部分那条"验证借阅证"的演变链讲，五步是推导不是堆砌 |
| 借阅额度和罚金为什么定这个数？ | 按常见高校图书馆规则拟定，**且全做成可配置**（`borrow_policies`/`fine_rules` 表，FR-017 可改），不硬编码 |
| 为什么不直接加 JPA 注解？ | 第五部分决策 3：领域层被框架污染就没法独立测试；已用 `javac` 编译验证 |
| 顺序图和类图不是实验二的吗？ | 指导书实验一步骤 4 明确要求"各层类、接口及其交互（类图，顺序图）"，所以是实验一的正式内容；AI 手册把它们划到实验二，我们按指导书 |
| 数据库设计验证过吗？ | 验证过。MySQL 8.0.45 实跑，11 表 / 9 外键 / 6 唯一键 / 4 条 CHECK 全生效，含 4 条负向验证（见 `13-database-design.md` 6.2 节） |
| AI 生成的内容你怎么保证对？ | 三道关：① 人工确认假设取值 ② 可验证的都实测（javac 编译 + MySQL 实跑）③ 每次 commit 前看 diff，日志留痕 |
| 实验一为什么不写代码？ | 指导书实验一步骤只到设计；代码在实验二"用代码实现设计结果"。本次写的 36 个 Java 是**设计契约的可编译表达**，不是实现 |
| 你的图怎么画的？ | PlantUML 文本化 + Git 管理（`specs/*.puml`），类图包图用 Graphviz 渲染；一条命令重生成，见 `tools/render-uml.sh` |
