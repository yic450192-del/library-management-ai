# 20 · 界面设计 UI Design（指导书实验二步骤 2）

> 指导书原文：**界面元素的设计，以用例文本和交互图为基础，重点考虑从展现层进入领域层的消息，
> 得出可用性较高的界面。**
>
> 说明：AI 版实验二手册走的是纯 REST 后端路线，**没有界面设计这一节**。
> 但 Word 指导书明确要求，且这是"实验二步骤 2"的独立考点，因此单独成文。

## 1. 设计前提

| 项 | 决定 | 理由 |
|---|---|---|
| 平台 | Web（浏览器），桌面优先 | 管理员在借还台用台式机；读者用手机浏览器也可用（响应式） |
| 交互模型 | 表单 + 即时反馈，不做 SPA 富交互 | 实验量级；且借还流程本质是"扫码 → 确认"两步 |
| 输入设备 | **假设有条码扫码枪** | 扫码枪本质是"键盘输入 + 自动回车"。这个假设直接决定了界面焦点策略（见 6.3） |
| 语言 | 全中文，错误提示说人话 | 馆员不是程序员，不展示 `QUOTA_EXCEEDED` 这种码 |

### 1.1 三类用户的可用性目标不同

| 角色 | 使用频率 | 核心诉求 | 设计取向 |
|---|---|---|---|
| 图书管理员 | 每天数百次 | **快**。借一本书不超过 3 次输入 | 键盘流、焦点自动跳转、成功后保留证号 |
| 读者 | 偶尔 | **明白**。知道能借几本、什么时候还 | 一屏看全、状态用文字不用图标 |
| 系统管理员 | 每周一两次 | **别出错**。改规则影响所有人 | 二次确认、变更前后对比、留操作日志 |

## 3. 关键界面元素设计

### 3.1 UI-02 借书办理（管理员）

界面分三区：**输入区 → 读者信息区 → 确认区**。顺序与 UC-101 的基本流一一对应。

| # | 元素 | 类型 | 数据来源 | 交互 / 校验 |
|---|---|---|---|---|
| 1 | 借阅证号输入框 | 单行文本 | 扫码枪或手输 | 自动聚焦；回车即触发"读证"，**不设提交按钮** |
| 2 | 读者信息面板 | 只读卡片 | 预检接口 | 显示姓名 / 类型 / 学院 / 已借 / 可借 / 超期标记 |
| 3 | 状态徽标 | 文字标签 | 预检结果 | `可借`（绿）/ `已达上限`（黄）/ `有超期未还`（红）/ `证无效`（灰） |
| 4 | 馆藏条码输入框 | 单行文本 | 扫码枪 | 读证成功后才启用；回车触发借书 |
| 5 | 结果区 | 提示条 | 借书响应 | 成功显示"应还日期 2026-11-16"；失败显示人话提示 |
| 6 | 今日借出计数 | 文本 | 本地累计 | 让馆员知道自己办了多少笔 |
| 7 | 重置按钮 | 按钮 | — | 清空证号与条码，重置焦点到 1 |

**键盘流（关键）**：

```
扫证号 → [回车] → 显示读者信息、焦点自动跳到条码框
扫条码 → [回车] → 借书 → 清空条码框、焦点回条码框（保留证号，可连续借同一人）
按 [Esc] / 点重置 → 清空证号，焦点回证号框
```

**为什么不放"提交"按钮**：扫码枪自带回车，馆员手上拿着书和证，再让他点鼠标是多余动作。
不设按钮也避免了"扫完忘了点"这类操作失误。

### 3.2 UI-03 还书办理（管理员）

| # | 元素 | 类型 | 数据来源 | 交互 / 校验 |
|---|---|---|---|---|
| 1 | 馆藏条码输入框 | 单行文本 | 扫码枪 | 自动聚焦；回车触发还书 |
| 2 | 还书预览区 | 卡片 | 还书预览接口 | 题名 / 借阅人 / 借出日期 / 应还日期 / 是否超期 / **预计罚金** |
| 3 | 罚款提示 | 高亮条 | 预览结果 | 超期时红色显示"超期 15 天，应缴罚金 3.00 元"，让馆员当场告知读者 |
| 4 | 结果区 | 提示条 | 还书响应 | 成功 + 罚款单号 |
| 5 | 待处理预约提示 | 提示条 | 还书响应 | 若该题名有预约，显示"已通知预约读者取书" |

> **还书不需要输入借阅证**——这是指导书原文的规定，界面上就不该出现证号框。
> 界面与用例文本不一致是最常见的需求误读来源。

### 3.3 UI-05 图书检索（读者）

| # | 元素 | 类型 | 说明 |
|---|---|---|---|
| 1 | 搜索框 | 单行文本 | 匹配书名 / 作者 / ISBN |
| 2 | 类型筛选 | 下拉 | 中外文图书 / 中外文杂志 / 论文 |
| 3 | 只看可借 | 复选框 | 默认关闭；勾选后过滤 `availableCopies > 0` |
| 4 | 结果列表 | 表格 | 书名 / 作者 / 类型 / **可借数 ÷ 总数** / 操作 |
| 5 | 可借数显示 | 文本 + 配色 | `2/3` 绿色；`0/3` 灰色并禁用"预约"按钮的取书提示 |
| 6 | 分页器 | 组件 | 每页 20 条 |

### 3.4 UI-10 规则维护（系统管理员）

| # | 元素 | 类型 | 说明 |
|---|---|---|---|
| 1 | 规则类型切换 | Tab | 借阅规则 / 罚款规则 |
| 2 | 规则表格 | 可编辑表格 | 读者类型 × 最大册数 / 期限 / 可续借次数；借出物类型 × 宽限天数 / 日罚金 / 上限 |
| 3 | 变更高亮 | 单元格级 | 改动过的单元格描边，提交前能看出自己改了什么 |
| 4 | 生效说明 | 静态文本 | "仅影响此后发生的借还，已产生的记录不变" |
| 5 | 二次确认对话框 | 模态 | 列出"旧值 → 新值"再确认 |

## 4. 展现层 → 领域层的消息映射（本节是指导书要求的重点）

界面上的每个动作，最终都变成一次进入应用层的消息。下表把**界面元素**与
`14-api-spec.md` 的接口、`09-design-model.md` 的应用服务方法一一对齐。

### 4.1 借书界面（UI-02）

| 触发 | 消息 | HTTP | 应用服务方法 | 关键入参 | 返回给界面的东西 | 失败呈现 |
|---|---|---|---|---|---|---|
| 扫证号回车 | 读者资格预检 | `GET /api/borrow-cards/{cardNo}/eligibility` | `CirculationApplicationService.previewBorrow(cardNo)` | `cardNo` | 姓名、类型、已借数、可借上限、是否超期 | 灰色徽标 + "该证已挂起" |
| 扫条码回车 | 办理借书 | `POST /api/circulation/borrow` | `CirculationApplicationService.borrow(cmd, operator)` | `cardNo`、`barcode` | `loanId`、`dueDate` | 人话提示（见 6.1） |
| 点重置 | 无后端消息 | — | — | — | — | — |

**为什么预检与借书是两个消息**：预检是**展示需要**（让馆员看到读者还剩几本额度），
借书是**业务动作**。二者不能合并——合并会导致"扫了证就产生借阅记录"。

**预检不是授权**：`POST /borrow` 仍会完整重跑五步校验（`09` 算法 6）。
预检通过不代表借书一定成功（比如两次扫码之间读者在别处借满了）。
这一点必须在界面上体现：预检的"可借"只是提示，不是承诺。

### 4.2 还书界面（UI-03）

| 触发 | 消息 | HTTP | 应用服务方法 | 关键入参 | 返回 | 失败呈现 |
|---|---|---|---|---|---|---|
| 扫条码回车 | 还书预览 | `GET /api/circulation/return-preview?barcode=` | `CirculationApplicationService.previewReturn(barcode)` | `barcode` | 题名、借阅人、应还日期、超期天数、预计罚金 | "该条码不是本馆藏书" |
| 确认还书 | 办理还书 | `POST /api/circulation/return` | `CirculationApplicationService.returnItem(cmd, operator)` | `barcode` | `loanId`、`fine` | 同上 |

> 还书用**两次消息**而不是一次：预览让馆员在确认前看到"要罚多少钱"，
> 避免"点了还书才发现罚款 20 元，读者已经走了"这种现场冲突。
> 预览使用当前时间计算，与实际还书可能相差几秒——差值不影响天数，可接受。

### 4.3 检索与预约界面（UI-05 / UI-06）

| 触发 | 消息 | HTTP | 应用服务方法 |
|---|---|---|---|
| 点搜索 | 查询题名 | `GET /api/book-titles?keyword=&itemType=&availableOnly=&page=&size=` | `CatalogQueryService.search(criteria)` |
| 点条目 | 题名详情（含副本） | `GET /api/book-titles/{titleId}` | `CatalogQueryService.detail(titleId)` |
| 点预约 | 预约图书 | `POST /api/reservations` | `ReservationApplicationService.reserve(cmd)` |

### 4.4 规则维护界面（UI-10）

| 触发 | 消息 | HTTP | 应用服务方法 |
|---|---|---|---|
| 打开页面 | 读规则 | `GET /api/admin/borrow-policies`、`GET /api/admin/fine-rules` | `RuleAdminService.listAll()` |
| 提交某行 | 更新规则 | `PUT /api/admin/borrow-policies/{readerType}` | `RuleAdminService.updateBorrowPolicy(type, cmd)` |

### 4.5 小结：消息的三种性质

| 性质 | 例子 | 特征 |
|---|---|---|
| **查询消息** | eligibility、return-preview、search | 幂等、无副作用、可重复发 |
| **命令消息** | borrow、return、reserve | 有副作用、必须事务、必须重复校验 |
| **配置消息** | update-policy | 低频率、影响面大、需二次确认 |

> 界面设计真正的产出不是"画得好看"，而是**把界面动作翻译成对领域层的消息，并区分它是哪一种**。
> 分不清查询与命令，就会出现"预览接口顺手把数据改了"这类事故。

## 5. 页面流转

```
UI-01 登录
  ├─ 角色 = Librarian  → UI-02 借书办理 ⇄ UI-03 还书办理 ⇄ UI-04 读者借阅查询
  ├─ 角色 = Reader     → UI-05 图书检索 → UI-06 详情与预约 → UI-07 我的借阅
  └─ 角色 = SystemAdmin → UI-08 借阅证管理 / UI-09 题名馆藏 / UI-10 规则维护

UI-02 成功后停留本页（连续借书），不清回登录
UI-06 预约成功后 → UI-07「我的预约」可见
```

**为什么借书成功不跳页**：借还台是流水作业，一跳页就要重新导航回来，一天几百次的操作成本极高。

## 6. 可用性设计要点

### 6.1 错误提示：把错误码翻成人话

| code | 界面提示 | 界面动作建议 |
|---|---|---|
| `CARD_NOT_FOUND` | 该借阅证号不存在，请核对后重扫 | 清空证号框、焦点回证号框 |
| `CARD_NOT_ACTIVE` | 该借阅证已挂起或注销，请联系系统管理员 | 保持证号框内容，便于核对 |
| `QUOTA_EXCEEDED` | 该读者已借满 5 册，请先归还 | 停留本页，不启用条码框 |
| `OVERDUE_LOAN_EXISTS` | 该读者有超期未还图书，需先归还 | 提供"查看超期清单"链接 |
| `ITEM_NOT_AVAILABLE` | 该书已被借出，请换一本 | 清空条码框，保留证号 |
| `ITEM_NOT_OWNED` | 该条码不是本馆藏书 | 清空条码框 |

> 提示语写"该怎么办"而不是"哪里错了"。`已达借阅上限` 是错误码的翻译，
> `该读者已借满 5 册，请先归还` 才是可用性。

### 6.2 防误操作

| 场景 | 措施 |
|---|---|
| 管理员误删题名 | 删除前展示该题名下副本数与预约数，二次确认 |
| 改规则影响所有人 | 展示"旧值 → 新值"对比，二次确认 |
| 读者误点预约 | 预约成功后提供"取消预约"入口（UC-004 已支持） |
| 还书 | **不做二次确认** —— 高频操作，加了反而慢；误扫可撤销（同一副本再次借出即可） |

### 6.3 焦点与键盘

| 规则 | 理由 |
|---|---|
| 页面进入即聚焦第一个输入框 | 扫码枪无需鼠标 |
| 输入框内回车 = 提交该区消息 | 扫码枪自动回车 |
| 借书成功焦点回条码框、保留证号 | 连续借同一人的多本书 |
| 还书成功焦点留在条码框 | 连续还多本 |
| `Esc` 清空当前输入并复位焦点 | 扫错时的快速纠正 |

### 6.4 加载与并发

| 场景 | 设计 |
|---|---|
| 请求中 | 输入框禁用 + 提交按钮转圈；防重复扫码 |
| 超过 3 秒 | 显示"正在处理，请勿重复扫码" |
| 乐观锁冲突 `CONCURRENT_MODIFICATION` | 提示"该书刚被他人借出，请重新扫码"，不自动重试（重试可能掩盖真实的库存竞争） |

### 6.5 信息呈现优先级

读者最关心的三件事，按此顺序排布：**能不能借 → 还剩几本 → 什么时候要还**。
界面上的字号与位置按此顺序递减，不用图标代替文字（老年读者与教师用户不一定理解图标语义）。

## 7. 界面与设计模式的对应

| 界面 | 用到的模式 | 说明 |
|---|---|---|
| 借书 / 还书 | **Form + 命令对象** | 界面把输入装成 `BorrowCommand` / `ReturnCommand`，应用层只认命令对象，不认 HTTP |
| 检索列表 | **DTO 投影** | 列表只查展示所需字段（`availableCopies` 由后端聚合），不返回整个实体 |
| 规则维护 | **表格 + 批量提交** | 一次提交多行，应用层逐行校验后整体事务 |
| 全局 | **MVC** | 界面 = View；Controller 只做协议转换；业务判断全在应用服务 |

## 8. 本次不做的界面（明确边界）

| 不做 | 原因 |
|---|---|
| 真实前端实现（Vue/React） | 指导书要求"界面元素的设计"，不是前端工程；程序实现的主角是后端分层 |
| 移动端专属适配 | 读者端用响应式即可，不做独立 App |
| 罚款在线支付 | `FineStatus.PAID` 已预留，无支付流程（见 `14-api-spec.md` 第 4 节） |
| 条码枪驱动对接 | 假设为键盘输入设备，无需驱动 |

> 线框图（`20a-ui-wireframes.puml`）是**结构示意**，不追求像素级还原。
> 它的作用是让"界面元素 → 消息"的映射有实物可指，答辩时能指着说清哪个控件发哪条消息。
